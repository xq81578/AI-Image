# 视频号发布与交付

本项目用户已授权：视频完成后，由统筹 Codex 使用默认浏览器全权负责视频号发布，包括登录判断、上传、填表、发表与结果核验；需要登录时通过 Telegram 向本人发送实际二维码。此授权适用于手动出片、定时出片和恢复发布，无需每轮或逐项询问是否发布。

## 浏览器发布约定

- 发布前读取 `ego-browser` 技能并运行 `ego-browser skill`，遵守当前工具的操作和控制权规则。使用用户指定浏览器；未指定时复用默认浏览器（当前为 Ego Lite）及已有视频号助手页面和登录状态。同一发布任务使用一个任务空间；完成下述已有页面检查后，才决定是否新建。
- 由 Codex 根据实际页面完成发布，不运行 `social_upload_adapter.py`、`publish_video.py` 或 `打开视频号.bat`，也不把旧发布器的安装、`--smoke` 或 `--dry-run` 作为前置步骤。旧脚本仅保留历史代码，不作为失败后的自动回退入口。
- 继续使用 `codex_video.py` 管理执行权、视频哈希和发布进度。浏览器工具不可用、被拒绝访问或需要用户操作时，保存真实卡点；不自行切换浏览器、用户目录或旧发布器绕过限制。
- 发布事件记录实际浏览器工具、任务空间与页面标识、页面地址及必要的平台证据；不记录 Cookie 或登录凭据。历史脚本错误与本次浏览器结果分开记录，不能把过去一次失败当成本次结果。

设置参考：[用户提供的发布页面截图](../assets/video-publish-settings.png)。按当前页面识别控件与核对设置，不照搬旧截图坐标。

### 发布前先检查已有页面

1. 先读本批发布记录中的空间、页面和地址，再用 Ego 的现有任务空间及标签列表查找 `channels.weixin.qq.com` 页面。必须核对实际列表，不能仅凭旧标识判断页面仍在或已经消失。未完成此检查，不得直接调用 `taskSpace(新名称)`、`newPage()` 或启动另一个窗口；新空间的空白页不会自动复用用户已打开的标签。
2. 优先恢复本批仍存在的发布页面，其次复用用户已打开且账号匹配的视频号助手页面。用户已为发布打开页面并要求使用时，按 Ego 控制权规则接管该空间，必要时将现有标签 `adopt` 为受管页面，再核对账号和当前表单；不要为了得到 `p1` 而另开页面。遇到用户接管、待确认的控制交接或账号不明时，沿用现有停止与澄清规则。
3. 只有实际检查确认没有匹配页面，且发布状态允许开始或继续填表时，才新建一个任务空间并访问视频号助手。已有页面暂时不能访问、未取得控制或连接失败，不等于没有页面，不能通过新建绕过。复用登录状态也不等于复用了原标签页。
4. 在随后第一个 `publish-step` 事件的 `evidence` 中记录选择了哪一个已有页面；确需新建时，记录检查结果与新建原因。发布后保留用户原有标签和结果页，便于下次继续复用。

## 进度与恢复

全程持有本轮 `execution.token`，每批连续网页操作开始前核对 `ownership`，从中断或用户控制恢复后、最终发表前重新核对，失去执行权立即停止。`finish` 为新完成的视频创建独立的 `publish-progress.json`，制作状态仍为 done。发布或通知交付没有完成时，后续 `begin` 恢复同一批次，不重新出片。升级前没有发布进度的历史成片不会被自动补发。

```powershell
python codex_video.py publish-status --run <批次>
python codex_video.py publish-init --run <批次> --token <执行凭证> --file <发布资料JSON>
python codex_video.py publish-step --run <批次> --token <执行凭证> --file <事件JSON>
```

发布进度以 `publish-progress.json` 为准，不手改状态。`publish-init` 保存文案、设置和视频哈希，相同资料重复执行返回原进度，不重置已提交状态；首次提交前为满足页面字数限制修改文案，可再次初始化并重新核对表单，曾经提交后禁止覆盖原资料。事件 JSON 至少含 `status` 与真实 `evidence`，可附页面地址、截图路径、二维码事件键等必要依据；不要保存 Cookie 或登录凭据。进度依次为 `awaiting_publish`、`prepared`、`waiting_login`（需要登录时）、`uploading`、`ready`、`submitting`、`published`、`delivered`（通知交付完成）；提交前的阻塞记为 `blocked`，提交结果不明记为 `uncertain`。

- `done` 且发布未完成：直接恢复本节，不再生图、render 或清理素材。
- `waiting_login`：找回本次默认浏览器页面和二维码通知回执，继续等登录；同一码不重复发。
- `uploading` 或 `ready`：重新读实际页面，确认文件和表单是否还在，不能仅按本地状态判断上传已完成。
- `submitting` 或 `uncertain`：先查平台结果或作品列表，禁止直接再次点击发布。取得匹配本条视频的成功记录则登记 published；只有明确确认未提交成功时，才从 uncertain 用 `confirmed_not_submitted: true` 和实际证据重新登记 ready；若仍是 submitting，先登记 uncertain。列表暂时没出现不能证明未提交。
- `published`：不再上传或发表，只补发尚未完成的通知；`delivered` 不再执行任何发布或通知。
- 恢复曾由旧脚本处理的批次时，先确认旧上传器已停止并读取原提交记录，不能与仍运行的上传器同时操作，也不能清除 submitting/uncertain 后重新发表。

## 准备发布资料

在本批次目录准备 `publish-info.json` 和便于复制的 `发布文案.txt`。成片审核完成后，围绕本轮乡村画面和时间变化，拟定一句与观众交流的问题。让观众想起自己的经历、牵挂或未来去向，愿意用自己的话接下去。语气自然亲近，情绪落在熟悉的小事、人与故乡关系的变化或具体时间跨度上，给观众留下自己的答案。

根据本轮画面，从以下方向选择合适的切入，轮换使用，不把示例当成每次固定套用的模板：

- 熟悉的日常：从喊小名、叫吃饭、村里熟人等细节唤起记忆，例如“现在回村，还有人喊你小名吗？”“小时候全村都认识你，现在呢？”。
- 长大后的归属与关系：问出时间过去后，人与故乡、旧相识之间的变化，例如“从哪一年起，回老家成了做客？”“那时候天天见的人，多久没见了？”。
- 未来的时间想象：给出具体跨度或未来年份，请观众想象那时自己、家人或老家的生活。用户偏好的语气参考是“再过60年也就是2086年，那时候你们都在干嘛呢？”；发布时可精炼为“再过60年，你会在干嘛呢？”或“到了2086年，你会在哪里呢？”。同时写跨度与年份时，按实际发布年份计算，不能长期照抄 2086；例如 2026 年加 60 年为 2086 年。给观众留出对未来的不同想象，不替他们断言结局。

先拟定三个切入不同的候选问题，再选择读起来最自然、有具体记忆或想象空间、容易接着讲自己的经历，且贴合整轮时间变化的一句。避免“你们村怎么样？”这类过宽的泛问，也不再默认使用“以前很热闹，现在没人了”这类替观众总结情绪的陈述句。不堆砌“岁月、旧梦、重逢、归途、光阴”等抽象抒情词，不用“评论区告诉我”代替问题本身。不得为了煽情虚构真实经历或把生成场景说成历史纪实、实地拍摄或真人经历。

选中句去除标点和空格后仍须为 7~15 个汉字、字母或数字；原稿较长时压缩铺垫，保留具体细节或未来时间提问。`description` 使用选中句子的原文，可带逗号、问号等标点；`short_title` 使用同一句话去掉全部标点和空格后的版本；发布资料中的话题只放在 `hashtags`，由 Codex 填表时追加到视频描述。平台“视频标注”会声明虚构内容，不再把“AI 创作场景”等说明塞进描述。示例结构：

```json
{
  "run_id": "本轮批次",
  "video": "本批次实际成片绝对路径",
  "short_title": "再过60年你会在干嘛呢",
  "description": "再过60年，你会在干嘛呢？",
  "hashtags": ["旧时光", "物是人非", "怀旧", "时光对照"],
  "settings": {
    "location": "不显示位置",
    "collection": "旧时光",
    "link": null,
    "activity": "不参与活动",
    "schedule": "不定时",
    "original_requested": true,
    "ai_label": "内容为虚构剧情，仅供娱乐"
  }
}
```

用 `publish-init` 登记后按返回的 `info` 填表，不能在普通重试时换成另一条视频或另一份文案。首次提交前需要按页面字数限制调整文案时，更新本轮资料并再次 publish-init，重新登记 uploading、核对表单并 ready。若提交结果曾为 uncertain，只有先取得明确的未提交证据并以 `confirmed_not_submitted: true` 恢复 ready，才允许修正文案后重新 publish-init；视频仍禁止更换，不能修改进度绕过检查。

## Codex 操作浏览器发布

1. 读取 `ownership`、`publish-status` 和本批 `info`，根据前述恢复规则决定继续填表、核对历史提交或仅补通知。在默认浏览器中找到视频号助手页面，核对实际账号与本批已有记录；账号不一致时先澄清，不直接提交。
2. 已登录时直接继续。需要登录时登记 waiting_login，从实际登录页截取完整二维码，用 `$telegram-notify` 的 document 模式发送。沿用 `time-echo:<run_id>:login-qr:<序号>`，把二维码 SHA256、事件键和 sent/already_sent 回执写入发布事件；同一码不重复发，刷新后有新码才使用下一序号。浏览器工具要求交还控制时执行 handOff 并等待用户确认，再恢复同一任务空间；以页面实际登录成功为准。等待超时或仍需验证时保存 blocked 并通知，不反复刷新刷码。
3. 登记 uploading，使用 `info.video` 的绝对路径上传原成片；等待页面明确完成上传、视频预览或处理就绪，不能把选中文件当成上传完成。根据 `description` 和 `hashtags` 填写视频描述，并填写同句去标点的 `short_title`。
4. 按 `info.settings` 设置不显示位置、合集“旧时光”、无链接、不参与活动、不定时、声明原创和视频标注“内容为虚构剧情，仅供娱乐”。原创声明须勾选协议、等待确认按钮启用、点击“声明原创”并确认弹窗关闭及勾选状态生效。
5. 发表前统一核对原视频、上传完成、完整文案与话题、短标题、上述全部设置、无标题错误及“发表”按钮启用。通过 `publish-step` 登记 ready，必须带真实 `account`、`evidence` 和下面全部检查项；只把实际核对通过的项设为 true。

```json
{
  "status": "ready",
  "account": "页面实际账号",
  "evidence": "本轮页面实际核对结果",
  "checks": {
    "video": true, "upload_complete": true, "description": true,
    "short_title": true, "location": true, "collection": true,
    "link": true, "activity": true, "schedule": true,
    "original": true, "ai_label": true
  }
}
```

6. 随后通过 `publish-step` 保存 submitting 事件，成功落盘后才点击一次“发表”。点击超时、中断或返回不明时不补点、不换工具重试、不重新上传，转入结果核验。
7. 平台出现与本次提交对应的“已发表”或“发表成功”时，登记 published，`receipt` 保存实际提示；没有明确提示时，在同一页面进入作品列表，按完整文案、话题、原提交时间核对，必要时比对封面和时长。只有匹配本条作品才登记 published；未找到或仍无法判断时登记 uncertain（原因 `UNCERTAIN_SUBMISSION`），保留页面并通知用户核对。列表暂时没有作品不构成“未提交”的证据。
8. 按浏览器技能结束或交还任务空间，保留用户原有标签及需要查看的结果页；不关闭用户浏览器或清除登录态。之后按下节通知、登记 delivered 并释放本轮执行权。

## 减少发布等待

- 首次观察取得足够的表单与定位信息后，将已知且无中间判断依赖的连续操作放在一次工具调用中，例如填写描述和短标题。不要每点一次就回到模型读取整页。
- 弹窗、下拉选项、页面跳转或操作失败时，再读取发生变化的相关区域；优先可见控件和局部快照，只有核对范围确实需要时才读整页。文本快照够用时不同时截图。
- 等待上传、选项或确认按钮等可观察状态，不用固定长延时。普通定位失败后先检查当前局部状态；嵌套页面或 Shadow DOM 可使用浏览器工具文档支持的方法处理，目标须来自当前页面且唯一、可见、可操作，不盲试旧定位或坐标。
- 全部设置完成后统一核对一次；已获得明确成功证据就登记结果，不反复从多个页面确认。合并操作不能跳过原创二次确认、提交意图落盘或重复提交防护。

## 发布结果与交付

Codex 依据平台证据登记 `published` 后，将发布结果通过 Telegram 发给本人，事件键 `time-echo:<run_id>:published`，提供标题、账号、平台状态与可用作品链接。没有平台成功证据时，不能发送“发布成功”。

## 成片通知与结束

成片审核后可先发送完成消息与 MP4，再由 Codex 操作浏览器发布。完成消息应说明“视频已完成，接下来发布”，而不是“已经发布”。事件键继续使用 `time-echo:<run_id>:complete` 和 `time-echo:<run_id>:video`；正文分别保存到 `telegram-complete.txt`、`telegram-video.txt`。MP4 超过通知技能附件限制时保留本机文件并说明。

通知返回 sent/already_sent 后保存真实回执；不确定或失败按通知技能处理。通知失败不重做视频、不重发作品；published 批次恢复时仅补通知。成片完成消息、MP4 和发布结果通知都取得回执后，登记 delivered 事件：notification_receipts 包含 complete、video、published 三项，每项保留 Telegram 通知脚本返回的 status（sent 或 already_sent）与 message_id。视频因超过附件上限而未发送时，仅 video 可使用 status=skipped_oversize 并记录 reason；仍需成功发送说明与发布结果。只有 delivered 后下一次 begin 才开始新视频。后台状态无变化保持安静，只在二维码需要操作、完成、失败或其他实质变化时提醒。

提交前卡点用 publish-step 记 blocked，已提交但结果不确定用 uncertain。发送简短原因、保留的进度和用户需要做的一步操作，事件键 `time-echo:<run_id>:blocked:<原因短码>`，相同卡点不重复通知。成片后的问题不使用制作阶段 block 改坏 done 状态。完成交付或保存阻塞并通知后 release；正在等扫码时仍持有执行权。Codex 本身停止运行时不能保证继续等登录或发送提醒，下次从本批次恢复。

登录态在默认浏览器中跨批复用。临时二维码保存在本批临时目录，发送结束后仅清理本次二维码，不删除浏览器会话数据。浏览器被用户接管时按工具规则停止操作；只有恢复控制后才继续。定时运行缺少浏览器工具或需要用户验证时，保存进度并通知，不能承诺在 Codex 停止后继续等待。
